## 1. 색

### 토큰

| 이름 | 밝은 테마 | 어두운 테마 | 쓰임 |

| `--faint` | `#9AA09D` | `#6E736F` | 라벨·비활성 |

| `--surface` | `#FBFAF7` | `#1B1F1E` | 카드·프레임 |
| `--surface-2` | `#F5F3EE` | `#232827` | 입력칸·눌린 영역 |
| `--line` | `#E2DFD8` | `#2E3433` | 구분선 |

| `--amber-soft` | `#F5EEDC` | `#2B2519` | 주의 배경 |
| `--on-accent` | `#FFFFFF` | `#10201C` | **강조색 위에 올라가는 글자** |

### 왜 이 색인가

**청록(`#2F6F62`)을 골랐다.** 남색은 기업·금융 톤이라 딱딱하고, 테라코타·크림 조합은 지금 AI가 만드는 페이지의 전형이다. 핵심 사용자가 20~30대 초반이라 신뢰감은 유지하되 관공서처럼 보이면 안 된다.

**회색에 초록 기운을 섞었다.** 순수한 중간 회색은 "고르지 않은" 느낌을 준다. 강조색 쪽으로 미세하게 치우친 회색은 선택된 것처럼 읽힌다.

**바탕은 종이에 가깝다(`#F2F0EB`).** 순백은 차갑고, 크림(`#F4F1EA`)은 흔하다. 그 사이에서 채도를 낮췄다.

### 규칙

* **`--on-accent`는 반드시 토큰으로 쓴다.** 강조색 위 글자를 `#fff`로 직접 쓰면 어두운 테마에서 읽히지 않는다.
  > 실제로 겪은 사고다. `:root:not([data-theme="light"]) .btn{color:#10201C}`이 `.btn.ghost{color:...}`보다 우선순위가 높아 보조 버튼 글자색을 덮어썼고, 어두운 배경에 어두운 글자가 됐다. **선택자로 싸우지 말고 토큰으로 푼다.**
* **의미색(주의·위험)은 강조색과 별개다.** `--amber`는 대기·경고, `#B4553C`는 되돌릴 수 없는 동작(삭제·회수)에만.
* **세 가지 테마 상태를 모두 설계한다.** 명시적 밝음 / 명시적 어두움 / **아무 표시 없음(기본값)**. 기본값 상태에서는 `prefers-color-scheme`만이 판단 근거다.

## 2. 서체

| 역할 | 서체 | 쓰임 |
| --- | --- | --- |
| 표제 | **Gowun Batang** (고운바탕) | 화면 제목, **되묻기 질문** |
| 본문 | **IBM Plex Sans KR** | 나머지 전부 |

### 왜 이 조합인가

**명조와 산스의 대비가 곧 서비스의 구조다.** 고민을 쓰고 조언을 받는 일은 *글*이다. 제목에 명조를 쓰면 "편지"의 질감이 생기고, 본문은 산스라 읽기 편하다. Inter·Space Grotesk는 지금 어디서나 쓰이는 기본값이라 피했다.

**되묻기 질문에만 본문보다 큰 명조를 쓴다.** 아래 §4-1 참조.

### 규칙

* 본문 기준 14.5px / 행간 1.65~1.85. 한글은 라틴보다 행간이 더 필요하다.
* 제목에 `text-wrap: balance`.
* 숫자가 세로로 줄 맞춰야 하는 곳(경과 시간, 개수, 점수)은 `font-variant-numeric: tabular-nums`.
* 대문자 라벨에는 `letter-spacing: .09em~.12em`.

## 4. 이 서비스만의 규칙 4가지

다른 프로젝트에 그대로 옮기면 안 되는, 참늘의 도메인에서 나온 규칙들.

### 4-1. 되묻기 질문은 본문보다 크다

조언은 **방향 / 되묻기 질문 / 함께 볼 것** 세 덩어리다. 보통은 본문이 가장 크지만, 이 서비스는 **답을 주는 게 아니라 생각을 돕는다.** 그 철학이 화면에서 안 보이면 그냥 "답변 받는 앱"이 된다.

* 읽는 쪽(#27): 질문만 명조 18.5px, 여백 넉넉히, 번호는 작게.
* 쓰는 쪽(#28): 그 입력칸만 강조 테두리 + `이 서비스의 핵심` 배지.
* **양쪽이 같은 용어를 쓴다** — 쓰는 쪽에서 "되묻기 질문"이라고 부르면 읽는 쪽에서도 그렇게 부른다. 그래야 조언가가 "내가 쓴 그 칸이 저기 보이는구나"를 안다.

### 4-2. 기다림을 숨기지 않는다

확인 절차를 거치므로 즉답이 없다. 로딩 스피너로 가리지 말고 **진행 타임라인**으로 드러낸다.

> 등록됨 → 조언가 배정 → 조언 도착 → 마무리

기다리는 게 **부실해서가 아니라 검수하느라**라는 게 보이면, 기다림이 오히려 신뢰 신호가 된다.

### 4-3. 막힌 버튼은 왜 막혔는지 말한다

백엔드에 시스템 잠금 방지 가드가 여럿 있다(자기 자신 관리자 회수 / 마지막 관리자 / 미보유 역할 / 낙관적 잠금). **눌러서 실패하는 것과 처음부터 이유가 보이는 건 다른 도구다.**

* 비활성 버튼 옆에 **조건이 언제 풀리는지**까지 적는다.
* 조건이 여럿 걸려 있으면 **하나의 카드에 ①②로** 적는다. 같은 대상에 같은 버튼이 두 번 비활성으로 뜨면 혼란스럽다.

### 4-4. 빈 상태의 감정가는 같지 않다

"아직 없다"와 "다 처리했다"는 다른 소식이다.

* 사용자·조언가의 빈 상태 → 회색 마크, 다음 행동 제시.
* **운영의 빈 대기열 → 청록 체크.** 빈 화면이 좋은 소식인 유일한 자리다.

| 역할 | 폭 | 이유 |

## 6. 문체

### 규칙

* **존댓말, 짧게.** "~해주세요" / "~할 수 있어요". 명령조("입력하시오")도, 과한 친근함("고민 있으세요? 😊")도 아니다.
* **버튼은 일어날 일을 그대로 말한다.** "확인" 대신 "고민 남기기", "제출" 대신 "확인 요청 보내기".
* **과안내하지 않는다.** 화면에서 이미 보이는 걸 문장으로 또 적지 않는다.
  > 알림 화면의 "진행에 변화가 있을 때만 알려드려요"는 삭제했다 — 알림 목록을 보면 아는 사실이다.
* **오류는 사과하지 않는다.** 무엇이 / 왜 / 무엇을 하면 되나, 세 층으로 적는다.

### 오류 문구의 세 층

```
무엇이   이 고민을 찾을 수 없어요
왜       지워졌거나, 내 고민이 아닐 수 있습니다.
왜 그런  남의 고민은 "없다"고 답합니다 — 있는지 없는지조차
         알려주지 않기 위해서예요.
다음     [ 내 고민으로 ]
```

세 번째 층(**왜 그렇게 동작하는가**)은 백엔드의 설계 결정이 사용자에게 고장처럼 보일 때만 붙인다. 404/403/412가 그 경우다.

### 용어

| 쓴다 | 안 쓴다 | 이유 |
| --- | --- | --- |
| 되묻기 질문 | 성찰 질문, reflective questions | 쓰는 쪽·읽는 쪽 공통 |
| 확인 절차 | 검수, 심사(조언에 대해) | 사용자에게는 절차, 운영에게는 검수 |
| 조언가 | 멘토, 전문가 | 실명·자격 대신 경험을 본다는 태도 |
| 인생 선배 / 전문가 | senior / expert | 사용자에게 보이는 lane 표기 |
| 남기다 (고민을) | 등록하다, 작성하다 | 행위가 가볍게 느껴져야 첫 글을 쓴다 |

## 7. 컴포넌트 원칙

* **모든 게 카드가 아니다.** 테두리·채움·둥근모서리·그림자는 각각 "별개의 것"이라는 신호다. 전부에 같은 둥근모서리와 그림자를 찍으면 위계가 사라진다.
* **보조 버튼은 색을 빼지 말고 채도를 뺀다.** 글자는 본문과 같은 강도로 읽혀야 한다. 흐릿한 보조 버튼은 "선택지가 아니다"라고 잘못 말한다.
* **되돌릴 수 없는 동작만 붉은색.** 삭제·역할 회수. 반려는 주의색(호박), 취소는 보조 버튼.
* **숨김은 호스트 CSS에 기대지 않는다.** `display:flex`가 `[hidden]`을 이긴다. 필요하면 `.x[hidden]{display:none}`을 직접 쓴다.

## 8. 접근성 기준선

* 키보드 포커스에 보이는 테두리(`:focus-visible`).
* `prefers-reduced-motion` 존중.
* 상태는 색만으로 말하지 않는다 — 점·모양·글자를 함께 쓴다.
* 자동완성·휠 같은 커스텀 입력에도 방향키·Enter·Esc가 동작한다.

## 10. 이 디자인 작업이 찾아낸 것

화면을 그리는 일은 명세를 읽는 것과 다른 종류의 검증이었다. **API에 없는 기능 두 가지**가 여기서 드러났다.

| 발견 | 내용 |
| --- | --- |
| 비밀번호 재설정 없음 | `auth/`에 가입·로그인·로그아웃·구글 2개뿐 |
| 고민 수정 없음 | `ConcernDetailView`에 `get`·`delete`만 |

둘 다 "사용자가 당연히 있을 거라 기대하는" 기능이다. 44개 엔드포인트를 명세로만 보면 빠진 게 보이지 않는데, **화면에 버튼을 놓으려는 순간** 드러났다.

> 이 프로젝트에서 같은 종류의 일이 반복됐다 — 알림 `target_url`은 소비자가 생기기 전까지 옳은지 알 수 없었고, 시스템이 맨바닥에서 일어서는지는 볼륨을 비워보기 전까지 몰랐다. **쓰는 쪽을 만들어야 읽는 쪽이 검증된다.**
