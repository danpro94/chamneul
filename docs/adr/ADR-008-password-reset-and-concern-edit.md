# ADR-008. 비밀번호 재설정과 고민 수정 — 엔드포인트 3건 추가 (44 → 47)

## Status

Accepted

## Date

2026-09-22

## Context

M5(Phase 2)가 끝난 뒤 MVP UI 프로토타입을 만들면서 **API에 없는 기능 두 가지**가 드러났다. 두 건 모두 "사용자가 당연히 있을 거라고 기대하는" 기능이다.

| 발견 | 실측 |
| --- | --- |
| **비밀번호 재설정 없음** | `accounts/urls.py`의 `auth/` 아래는 signup·login·logout·google/authorize·google/callback **5개뿐** |
| **고민 수정 없음** | `ConcernDetailView`에 `get`·`delete`만 있고 `patch`가 없다 |

44개 엔드포인트를 명세로만 읽을 때는 이 공백이 보이지 않았다. **화면에 버튼을 놓으려는 순간** 드러났다 — 로그인 화면에 "비밀번호를 잊으셨나요?"를 달 수 없고, 고민 상세에 "고치기"를 달 수 없다.

> 이 프로젝트에서 같은 종류의 일이 세 번째다. 알림 `target_url`은 읽는 쪽이 생기기 전까지 옳은지 알 수 없었고(SPEC-003), 시스템이 맨바닥에서 일어서는지는 볼륨을 비워보기 전까지 몰랐다(SPEC-004). **쓰는 쪽을 만들어야 읽는 쪽이 검증된다.**

CLAUDE.md §5는 Phase 2의 API 표면을 **44개로 고정**하고 있고, §16은 "changing MVP scope"를 Owner 승인 게이트로 규정한다. 따라서 엔드포인트 추가는 ADR 없이 진행할 수 없다.

## Decision

### 1. 엔드포인트 3건 추가 — 44 → 47

| # | Method | Endpoint | 용도 |
| --- | --- | --- | --- |
| 45 | POST | `/api/v1/auth/password-reset` | 재설정 요청 (메일 발송) |
| 46 | POST | `/api/v1/auth/password-reset/confirm` | 토큰 + 새 비밀번호로 확정 |
| 47 | PATCH | `/api/v1/users/me/concerns/{concern-id}` | 고민 수정 |

`/confirm`은 §7의 "명사, 동사 금지"에 대한 예외다. api.md §3이 `#33 /review`·`#41 /read`에 대해 이미 같은 예외를 선언했으므로 **새로운 예외를 만드는 것이 아니라 기존 예외 범주에 속한다**.

`#47`은 기존 경로(`#18` GET / `#19` DELETE)에 메서드를 하나 더하는 것이라 **새 URL 패턴이 생기지 않는다**.

### 2. 비밀번호 재설정 — 계정 존재 여부를 노출하지 않는다

`#45`는 **가입되지 않은 이메일에도 200을 반환**한다. "그런 계정 없습니다"라고 답하면 그 엔드포인트가 **가입 여부를 조회하는 도구**가 된다(CLAUDE.md §10 — 사용자 소유 데이터 보호).

* 토큰은 Django 기본 `PasswordResetTokenGenerator` 사용 — **서드파티 패키지 추가 없음**(§16 게이트 해당 없음).
* 유효기간 30분, 일회용(사용 후 무효).
* **Google로만 가입한 계정(로컬 비밀번호 없음)도 같은 200**을 반환하되, 메일 본문이 "이 계정은 Google 로그인을 씁니다"로 달라진다.

### 3. 메일 발송은 Phase 3 — 엔드포인트는 지금

`EMAIL_BACKEND`를 환경별로 나눈다.

| 환경 | 백엔드 | 결과 |
| --- | --- | --- |
| local / test | `console` (Django 내장) | 링크가 **터미널에 출력**된다 |
| prod | SMTP | Phase 3에서 실제 발송 서비스 연결 |

기능 검증은 콘솔 출력으로 가능하다. 실제 발송은 **코드가 아니라 인프라**(발송 서비스 계정, 도메인 인증)이므로 배포 시점에 붙이는 것이 순서다.

### 4. 고민 수정은 **배정 전까지만** (`SUBMITTED` 상태에서만)

`concern.status != SUBMITTED`이면 **409**.

수정 가능 필드는 생성 시 받는 필드와 같다 — `concern_summary` / `concern_type` / `concern_type_secondary` / `decision_context` / `preferred_advisor_lane` / `display_alias` / `is_anonymous`. `status`·`author`·`deleted_at`은 서버가 관리한다.

## Rationale (Why)

### 왜 "배정 전까지만"인가

핵심 긴장은 이것이다 — 사용자는 *"아 이것도 말씀드려야 하는데"* 하며 고치고 싶어 하는데, **조언가가 읽고 있던 글이 바뀌면 이미 쓴 조언이 다른 질문에 대한 답이 된다.**

네 가지 길을 검토했다.

| 안 | 방식 | 채택하지 않은 이유 |
| --- | --- | --- |
| 가 | **배정 전까지만** | — **채택** |
| 나 | 조언 도착 전까지 | 조언가가 **모르는 사이에** 원문이 바뀐다. "작성자가 고쳤습니다" 알림·표시·이력이 함께 필요해져 MVP 범위를 넘는다 |
| 다 | 언제든 수정 + 이력 보존 | 조언–고민 대응이 깨진다. 이미 전달된 조언이 무엇에 답한 것인지 사후에 알 수 없다 |
| 라 | 수정 대신 **덧붙이기** | **가장 좋은 답이지만 지금은 이르다** (아래) |

**가**를 택한 이유 셋:

1. **엔드포인트 1개로 끝난다.** 나·다는 조언가 쪽 UI·알림·이력이 따라온다.
2. **시간 창이 충분하다.** 배정에 보통 1~3일 걸리므로 수정 기회가 없지 않다.
3. **충돌이 구조적으로 불가능하다.** 상태로 막으므로 경합 처리가 필요 없다.

### 라(덧붙이기)를 Phase 3로 미루는 이유

원문은 고정하고 *"추가로 드리고 싶은 말"*만 덧붙이면 양쪽 요구가 다 풀린다 — 조언가가 본 글은 바뀌지 않고, 새 정보는 전달된다. 사용자 심리에도 맞다.

다만 모델을 하나 더 만들어야 하고, **실제 사용자가 "고치고 싶다"고 말하는 것을 본 뒤에** 만드는 것이 맞다. 지금 만들면 아무도 안 쓰는 기능을 유지보수하게 된다.

### 왜 상태 코드가 409인가

"배정된 뒤 수정 시도"는 요청 자체는 올바르고 **현재 상태와 충돌**하는 경우다(api.md §1.8 — 비즈니스 규칙 위반). 403(권한 미달)도 404(존재 은닉)도 아니다. 본인 고민이 맞고, 존재하는 것도 맞다.

## Trade-offs

* **배정이 예상보다 빨리 일어나면 수정 기회를 놓친다.** 배정은 관리자가 수동으로 하므로 사용자가 예측할 수 없다. 완화책은 UI가 *"조언가가 배정되기 전까지만 고칠 수 있어요"*를 **미리** 알리는 것이다(프로토타입에 반영됨).
* **메일 발송 없이 엔드포인트만 있으면 실사용에서는 반쪽이다.** 로컬·테스트에서는 완전히 검증되지만, 배포 전까지 실제 사용자는 비밀번호를 되찾을 수 없다. Phase 3의 필수 항목으로 [리뷰 노트 07](../reviews/07-phase2-closeout.md) §3에 추가한다.
* **`/confirm`이 URI 규칙의 예외를 하나 더 만든다.** 기존 예외(`#33 /review`, `#41 /read`)와 같은 범주이나, 예외가 셋이 되면 "예외"라기보다 패턴에 가까워진다. api.md §3의 예외 목록을 갱신해 **의도된 것임을 남긴다**.
* **재설정 요청에 레이트 리밋이 없다.** 같은 주소로 메일을 반복 발송시킬 수 있다. 브루트포스 방어와 함께 Phase 3 항목이며, 그때까지는 로컬 전용이라 실효 위험이 없다.

## Consequences

* **CLAUDE.md §5**가 개정된다 — 엔드포인트 수 44 → 47, 추가된 3건의 성격 명시. 개정은 본 ADR이 **Accepted**로 전환된 뒤에만 적용한다(§16 헌법 잠금 절차).
* **CLAUDE.md §16**에 본 ADR이 §5를 supersede함을 명시한다.
* `docs/api.md`에 #45·#46·#47 절이 추가되고, §3 요약표와 예외 목록이 갱신된다.
* `config/settings/{local,test}.py`에 `EMAIL_BACKEND = "django.core.mail.backends.console.EmailBackend"`가 추가된다. `prod.py`는 Phase 3까지 미설정으로 둔다.
* `accounts/`에 재설정 서비스·serializer·뷰가, `concerns/`에 수정 서비스·serializer가 추가된다. **모델 변경은 없다** — 토큰은 Django가 계산하므로 저장하지 않고, 고민 수정은 기존 컬럼만 건드린다.
* 구현은 `specs/SPEC-005-api-gaps/`에서 TDD 루프로 진행한다.
* STATUS.md의 엔드포인트 총계가 44 → 47로, 구현 상태가 44/47로 바뀐다.

## Validation

* `grep -c "^### [0-9]" docs/api.md`가 47을 반환하는지 확인.
* `#45`에 **가입되지 않은 이메일**을 보냈을 때 응답 본문·상태 코드가 가입된 이메일의 경우와 **바이트 단위로 동일**한지 테스트로 고정(계정 존재 은닉).
* 만료된 토큰·이미 쓴 토큰으로 `#46`을 호출하면 400이고, 그때 비밀번호가 **바뀌지 않았는지** 확인.
* `#47`을 `ASSIGNED`·`ANSWERED`·`CLOSED` 상태에서 호출하면 전부 409이고, **어느 필드도 바뀌지 않았는지** 확인.
* `#47`이 `status`·`author`·`deleted_at`을 받지 않는지(무시 또는 400) 테스트로 고정.
* 로컬에서 `#45` 호출 시 재설정 링크가 콘솔에 출력되는지 스모크로 확인.
