## 1. 무엇이 바뀌었나

두 리뷰가 **독립적으로 같은 문제 4건**을 지적했다(500 크래시, 삭제된 고민의 조언 노출, #32 미검증, 잠금 범위). 서로 다른 관점에서 같은 결론에 도달했다는 점이 신호였다.

### 반영한 수정 (코드 6건)

## 2. 가장 값진 발견: 헌법 충돌

`api-architect`가 잡은 것 중 코드 버그가 아닌 것이 하나 있다.

CLAUDE.md §6.7은 `version`을 "**every** advice update"마다 +1이라고 규정했는데, 2026-09-11 Owner 결정(SPEC-002 §7-2)은 "본문 변경 시에만"으로 좁혔다. 구현·명세·테스트는 새 규칙으로 일관됐지만 **ADR이 없었다**. §16 constitutional lock은 CLAUDE.md 변경을 "해당 조항을 명시적으로 supersede하는 새 ADR"로만 허용한다 — 즉 **코드가 헌법을 앞서 있는 상태**였다.

ADR-006이 만들어진 이유가 정확히 이런 drift를 막자는 것이었는데, 그 다음 SPEC에서 같은 유형이 재발했다. ADR-007로 메웠고, §16에 재발 방지 문구를 남겼다:

> **CLAUDE.md 조항과 충돌하는 SPEC 결정은 리뷰 때가 아니라 결정 시점에 ADR이 필요하다.**

## 3. 이 리뷰가 증명한 것

**AC 전항 통과는 "버그가 없다"와 다르다.** TASK-007에서 AC-1~AC-11을 전수 대조해 미커버 6건을 메웠고 168개 테스트가 통과했는데, 그 상태에서 리뷰가 **데이터 손실 버그 1건(M-1)과 500 크래시 1건(M-2)**을 찾았다.

이유는 분명하다. AC는 **내가 생각한 시나리오**의 목록이다. M-1은 "조언가 수정"과 "관리자 리뷰"가 **동시에** 일어나는 경우인데, 두 기능을 각각 구현할 때는 떠올리지 않은 조합이다. M-2도 "고민 삭제"와 "조언 리뷰"의 교차점이다. 둘 다 단일 기능 AC로는 잡히지 않는 **기능 간 상호작용**이다.

SPEC-001은 이 리뷰를 건너뛰고 머지했다. 같은 유형의 결함이 남아 있는지 별도 점검이 필요하다(아래 후속 참조).

## 4. DevOps 설명 포인트

* **`select_for_update`는 "읽고-고치고-쓰는" 구간 전체를 트랜잭션으로 감싸야 의미가 있다.** M-1은 잠금이 아예 없었던 게 아니라(`review_advice`에는 있었다) **한쪽에만** 있었던 사례다. 낙관적 잠금(412)도 관리자를 지켰을 뿐 관리자의 결정을 지키진 못했다 — 방어가 단방향이면 반대 방향은 그대로 뚫린다.
* **`save()`의 기본 동작은 전 컬럼 UPDATE다.** 인스턴스가 오래됐다면 그 오래된 값 전부를 쓴다. `update_fields`는 성능 최적화로 알려져 있지만, 여기서는 **권한 경계**로 쓰였다 — 조언가 경로가 리뷰 컬럼을 물리적으로 쓸 수 없게 만든다.
* **soft delete는 FK 역방향 조회에 자동 적용되지 않는다.** `Concern.objects`가 삭제 행을 감춰도 `Advice.objects.filter(concern__author=...)`는 `base_manager`를 타므로 그대로 통과한다. 이번 MJ-1의 원인이며, 소프트 삭제를 쓰는 모델이 늘면 반복될 함정이다.

## 5. 보안 노트

* 정보 노출 관점의 블로커는 없었다. 응답 필드 분리(`reject_reason`/`memo`/`author_nickname`), CSRF, 세션 정책, admin 게이트는 전부 의도대로 동작했다.
* 실재한 유일한 내부정보 노출 경로는 M-2의 500이었다 — `DEBUG=True`에서 트레이스백 전문이 응답에 실린다. 로컬 기본값이 `DEBUG=True`라 개발 중에는 상시 노출 상태였다.
* `IsActiveAdvisor`가 `active_role`만 보고 `UserRole` 보유는 확인하지 않는다. 현재는 `set_active_role`이 보유 역할만 허용해 안전하지만, **M4-8(역할 회수, #43)에서 회수 시 `active_role`을 강등하지 않으면 회수된 조언가가 #29~#31을 계속 통과한다.**
