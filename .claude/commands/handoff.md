`docs/learning/02` §6 explain-first 규칙을 따른다. **순서를 지켜라 — 이것이 규칙의 전부다.**

## 1단계 — 먼저 물어라, 그리고 기다려라

Owner에게 다음 5줄을 요청하고 **답을 받을 때까지 아무것도 쓰지 마라.**

```
## Owner 선요약 (AI 노트 읽기 전, 기억만으로)
1. 오늘 바뀐 것:
2. 왜 이 방식인가:
3. 요청이 흐르는 경로:
4. 가장 부서지기 쉬운 지점:
5. 아직 설명 못 하는 것:
```

내가 먼저 요약을 보여주면 이 장치는 무의미해진다. 재인(recognition)은 인출(recall)이 아니다.

## 2단계 — 선요약을 그대로 보존

받은 5줄을 활성 SPEC의 `handoff.md` **최상단에 원문 그대로** 넣어라. 다듬지 마라.

## 3단계 — diff가 노트의 본체다

그 아래에 **선요약과 실제 구현의 차이**를 짚어라. 이것이 이 노트의 존재 이유다.

* 맞게 기억한 것 — 짧게
* **틀리게 기억한 것 — 무엇을, 실제로는 어떤지**
* 아예 언급하지 않았는데 중요한 것

그 다음 사실 기록: 변경된 파일 / 왜 이렇게 구현했는지 / 검증 방법과 **실측 결과** / DevOps 설명 포인트 / 보안 노트 / 다음 개선.

## 4단계 — 학습 부채 갱신

선요약 5번("아직 설명 못 하는 것")과 3단계에서 드러난 오해를 `docs/00-project/LEARNING_DEBT.md` 형식의 행으로 변환해 보여줘라.

| # | 항목 | 등록 | 우선순위 | 상태 | 해소 근거 |

파일 수정은 Owner 확인 후에 한다.

## 5단계 — 대장 항목 초안

`README_AIUSAGE.md`에 추가할 항목 초안을 제시하라 (CLAUDE.md §13 필수 필드).

```
## YYYY-MM-DD — <제목>
* **작업**:
* **AI 도구**:
* **인간 결정**:
* **생성 산출물**:  ← 커밋 해시 포함
* **검증 결과**:    ← 실측만. 실행 안 한 것은 적지 마라
* **잔여 리스크**:
```

## 6단계 — STATUS 갱신 제안

`docs/00-project/STATUS.md`에서 바뀌어야 할 줄을 짚어라 — 활성 SPEC, 구현 현황, 다음 최소 작업 단위. 수정안을 보여주고 Owner 확인 후 반영한다.
