# SPEC-004 — Phase 2 종료 (M5: 스모크 테스트 + 문서 정리)

> 대상: CLAUDE.md §1 "Phase 2 completion means" 9개 조건 전항 충족. 엔드포인트 신규 구현 없음.
> Status: **Approved (2026-09-16)** — §5 결정 5건 Owner 승인 완료. TASK-001 착수.

## 1. 배경 — M5는 무엇을 닫는 마일스톤인가

M4가 끝나 api.md의 44개 엔드포인트가 전부 구현됐다(283개 테스트, 서브에이전트 리뷰 2종 반영). 그러나 **Phase 2가 끝난 것은 아니다.** CLAUDE.md §1의 완료 조건 9개 중 **2개가 아직 열려 있다.**

| 조건 | 상태 | 근거 |
| --- | --- | --- |
| Django 앱 로컬 구동 | ✅ | `docker compose ps` |
| PostgreSQL 컨테이너 | ✅ | 동일 |
| `/healthz` 200 | ✅ | `config/health.py` |
| 핵심 API 동작 | ✅ | 44/44, [STATUS.md §2](../../docs/00-project/STATUS.md) |
| Django Admin 데이터 확인 | ✅ | 각 앱 `admin.py` |

이 SPEC은 그 2개를 닫고, 그 과정에서 이전 마일스톤들이 "M5 스모크 노트에 기록"으로 미뤄둔 항목들을 회수한다.

### 왜 스모크 테스트가 중요한가

283개 테스트는 **전부 테스트 DB에서** 돌았다. 볼륨을 비운 진짜 새 컨테이너로 처음부터 올려 사용자 여정을 통과시켜 본 적은 **한 번도 없다.** 지금까지 확인한 것은 "코드가 의도대로 동작한다"까지이고, "시스템이 맨바닥에서 일어선다"는 미확인이다.

이 구분은 SPEC-003에서 이미 한 번 값을 치렀다 — 알림의 `target_url` 5종은 전부 옳았지만 **아무도 눌러본 적이 없어서** 옳다는 사실 자체가 미확인이었다. 스모크 테스트는 같은 종류의 공백을 시스템 전체 규모로 메운다.

## 3. TASK-001이 통과시킬 사용자 여정

컨테이너를 **완전히 새로** 띄운다(named volume 삭제 → `docker compose up` → `migrate` → `createsuperuser`). 그 위에서:

```
1. 회원가입 (#2)                    → 세션 쿠키 발급 확인
2. 로그인/로그아웃 (#3, #4)         → 서버 세션 삭제 확인
3. 고민 작성 (#16) · 목록 (#17)
4. 관리자: 고민 목록 (#22) · 배정 (#24)
5. 조언가: 역할 전환 (#10) · 배정 고민 열람 (#20, #21)
6. 조언가: 조언 작성 (#28)
7. 관리자: 리뷰 목록 (#32) · 승인 (#33)
8. 사용자: 받은 조언 (#26) · 상세 (#27)
9. 사용자: 피드백 (#34)
10. 알림: 목록 (#39) · 읽음 (#41) · target_url 이동
11. 관리자: 역할 회수 (#43) → 조언가 활동 차단 확인
```

**비정상 경로도 함께 통과시킨다** — DB를 내렸을 때 `/healthz`와 API가 어떻게 반응하는지(CLAUDE.md §11의 "what happens when DB is unavailable"), 마이그레이션 미적용 상태로 기동했을 때.

## 5. Owner 결정 — 5건 전부 승인 (2026-09-16)

| # | 결정 | 내용 |
| --- | --- | --- |
| **1** | **산출물 위치 = `specs/`** | ADR-006 §30·§59가 "계획 문서(reviews/)와 작업 단위(specs/)"를 분리했고, **AC를 갖는 작업 단위는 SPEC**이다. M2~M4의 `reviews/0N-definition.md`는 ADR-006 이전 패턴. STATUS.md §4 "Active SPEC"도 이 SPEC을 가리킨다 |
| **2** | **시각은 백엔드 전 구간 UTC** | **DB** = 항상 UTC 저장 / **백엔드 API** = 비즈니스 로직·네트워크 전송 모두 **ISO 8601 UTC**(`…Z`) / **클라이언트** = 사용자 기기 타임존을 감지해 현지 시각(KST 등)으로 변환. api.md §1.7·model.md §1.1의 "응답은 KST로 직렬화"를 이 정책으로 교체한다. `TIME_ZONE="UTC"` 설정은 그대로 — **코드가 아니라 문서가 틀렸다** |
| **3** | **#21을 403 → 404로 변경** | 배정되지 않은 조언가는 고민 id를 알 수 없으므로 403은 "그 고민이 존재한다"를 알려준다. api.md §1.8의 404 규칙(전적으로 사적인 자원)에 맞춘다. 새 규칙의 유일한 예외가 사라진다 |
| **4** | **학습 부채 14건 폐기** | Owner가 학습 세션 종료를 선언했다(2026-09-11). STATUS.md §6을 "종결"로 바꾸고 미해소 목록에서 제거한다 — 남겨두면 영원히 미해소로 보인다 |
| **5** | **고민 종료는 Django Admin으로만** | Phase 2에 `CLOSED` 전이 사용자 API를 추가하지 않는다(44개 계약 유지). CLAUDE.md §6.6 문구와의 긴장은 `docs/smoke-test.md`에 기록하고 Phase 3 후보로 넘긴다 |

결정 2·3은 §16 승인 게이트(동작·상태 코드 변경)에 해당하여 착수 전 승인을 받았다. CLAUDE.md에 시각 직렬화 규정이 없으므로(§6.6의 `timezone.now()` 언급뿐) 결정 2에 ADR은 불필요하다.

## 6. Non-Goals

* **신규 엔드포인트** — 44개 계약 고정. `CLOSED` 전이 API도 추가하지 않는다(결정 5).
* **AWS / K8s / Terraform / CI-CD** — Phase 3+ (CLAUDE.md §5).
* **브루트포스 방어 구현** — 갭으로 **기록만** 한다(Phase 3).
* **정적파일 서빙 구성** — 동일.
* **실제 경합 재현 테스트**(`TransactionTestCase` + 스레드) — Phase 3 후보. 잠금의 존재는 이미 SQL 수준 테스트로 고정돼 있다.
* **M4-1~M4-3 소급 테스트** — `accounts`의 회원가입·로그인·OAuth·프로필. 부채로 유지하고 Phase 3에서 다룬다.
* **프론트엔드 구현** — 결정 2가 프론트 책임을 명시하지만, 구현은 Phase 2 범위 밖.
